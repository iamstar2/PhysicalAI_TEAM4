## 2. 로컬 시험 설정 vs 팀 연동 설정 — 섞지 말 것

| 항목 | 로컬 시험 (D 담당 PC 단독) | 팀 연동 |
|---|---|---|
| 브로커 | D 담당 PC의 별도 mosquitto, **127.0.0.1:18883** | 팀 브로커 (`docker-compose.host1.yml` 기준 `<브로커 호스트 IP>:1883`) |
| 접속 범위 | **D 담당 PC 안에서만** 접속 가능. 127.0.0.1에만 열려 있어 다른 팀원 PC와 로봇은 접속 불가 | 팀원 PC 전체 |
| 대시보드 MQTT | `MQTT_HOST=127.0.0.1 MQTT_PORT=18883` | `MQTT_HOST=<브로커 IP> MQTT_PORT=1883` (팀 합의값) |
| 메시지 출처 | `tools/mock_publisher.py` 등 가짜 A | 실제 A/B/C 노드 |

- D 담당 PC는 Windows TCP 제외 범위에 1883이 들어 있어 **그 PC에서는 1883 브로커를 띄울 수 없다.**
  다른 PC의 1883 브로커에 접속하는 것은 문제없다. 예약 포트나 네트워크 설정은 바꾸지 않는다.
- 팀 연동 중에는 로컬 브로커로 시험 메시지를 보내지 않는다. 대시보드와 발행 도구가 서로 다른 브로커를 보면
  아무 일도 일어나지 않은 것처럼 보여 혼동된다.

## 3. 대시보드 실행 위치와 로봇 네트워크

- 10/03~10/04 시험 구성에서 로봇은 D 담당 PC의 모바일 핫스팟(192.168.137.0/24)에 연결돼 있었다.
- **다른 팀원 PC에서 로봇에 접근할 수 있는지는 네트워크 구성에 따라 달라진다.** 로봇과 같은 네트워크에 있거나
  라우팅이 되면 가능하고, 핫스팟 구성 그대로라면 다른 PC에서는 닿지 않을 수 있다.
  **지금까지 검증된 방식은 D 담당 PC에서 대시보드를 직접 실행하는 방식이다.**
- **Docker로도 실행할 수 있다.** 단 UDP 환경변수(`MECHDOG_D_DRIVER=udp`, `MECHDOG_D_UDP_HOST`, `MECHDOG_D_UDP_PORT`)를 넘기고,
  컨테이너에서 로봇 IP로 UDP가 나가는 네트워크 조건을 갖춰야 한다.
  **현재 팀 `docker-compose.host2.yml`의 `security-dashboard`에는 이 환경변수가 없어 기본값인 mock으로 동작한다.
  그대로는 실물 로봇이 움직이지 않는다.** 컨테이너에서 로봇으로 UDP가 나가는 구성은 아직 검증하지 않았다.
- **로봇 IP는 재부팅 후 바뀔 수 있으므로 현장에서 재확인한다**(10/03과 10/04의 IP가 달랐다).

## 4. 팀 연동 실행 순서

### 단계 1. 팀 MQTT 브로커 주소 / 포트 확인
1. 브로커 담당에게 받을 것: 브로커 호스트 IP, 포트(기본 1883), 인증 사용 여부.
2. 인증을 쓰면 `MQTT_USER` / `MQTT_PASS`는 실행하는 셸에서만 환경변수로 넣는다.
   **비밀번호를 문서·로그·채팅·Git에 적지 않는다.**
3. 대시보드 PC에서 연결을 확인한다(TCP만 확인, 메시지 발행 없음):
   `Test-NetConnection <브로커 IP> -Port 1883` → `TcpTestSucceeded : True`
   - 실패하면: 같은 네트워크에 있는지, 브로커 PC 방화벽, 포트 공개 여부를 확인한다.

### 단계 2. 로봇 현장 IP 재확인 → 대시보드 UDP 대상 설정
1. 로봇 전원과 WiFi 연결을 확인한다. 다리는 바닥에서 뜨게 고정한다.
2. USB 시리얼 friendly REPL로 읽기 전용 확인을 한다. 짧은 명령만 쓰고 에코를 대조하며, Ctrl-C와 리셋은 쓰지 않는다:
   `wifi.wlan.isconnected()`, `wifi.wlan.ifconfig()[0]` → 현장 IP를 기록한다. 포트는 9027 고정.
3. `ping <로봇 IP>`로 응답을 확인한다. 첫 응답이 느리거나 1회 유실될 수 있다(10/03 관찰).

### 단계 3. 최신 코드로 대시보드 실행
1. 이전 시험용 대시보드가 떠 있으면 먼저 종료한다(3000번 포트 충돌 방지).
2. **첫 실행은 mock 드라이버**로 해서 A 메시지가 들어오는지만 확인한다(로봇 동작 없음):
   ```bash
   cd security-dashboard
   MQTT_HOST=<브로커 IP> MQTT_PORT=1883 PORT=3000 MECHDOG_D_DRIVER=mock \
     python app/main.py > <로그 파일> 2>&1
   ```
   - 로그: `[mqtt] connected (rc=0)`와 구독 4건이 보여야 한다.
   - 화면: `MQTT 연결됨`, 노드 상태(A/B/C 하트비트가 들어오면 표시).
3. A 메시지가 `[state] ...` 로그로 들어오는 것을 확인하면 대시보드를 종료하고 **UDP 드라이버로 다시 실행**한다:
   ```bash
   MQTT_HOST=<브로커 IP> MQTT_PORT=1883 PORT=3000 \
   MECHDOG_D_DRIVER=udp MECHDOG_D_UDP_HOST=<단계 2의 로봇 IP> MECHDOG_D_UDP_PORT=9027 \
     python app/main.py > <새 로그 파일> 2>&1
   ```
   - 로그 파일은 실행할 때마다 새 이름을 쓴다(`>`는 덮어쓰기라 이전 증거가 사라진다).
   - 화면에서 드라이버 `UDP(실물)`과 활성 경고 0건을 확인한다. 브라우저는 Ctrl+F5로 새로고침하고, 대시보드 탭은 **하나만** 연다
     (10/04에 열려 있던 다른 탭에서 해제 요청이 들어간 기록이 있다).
4. UDP 대상 주소는 첫 명령이 나갈 때만 로그에 찍힌다. 첫 경고 때 `SENT ... -> <로봇 IP>:9027`을 확인한다.

### 단계 4. A의 실제 판정 수신 (미인가 / 안전모 / 조끼)
한 번에 한 시나리오씩 A 담당과 말로 맞춘 뒤 진행한다.
순서: 관찰 → 관리자 해제 → 파란 눈·기본 자세 확인 → 다음 시나리오.

| 순서 | A 입력 (같은 session_id) | 대시보드 예상 | 로봇 예상 |
|---|---|---|---|
| 4-1 미인가 | face unauthorized | ALERT, '미인가 인물' 카드 | 빨간 눈 → 두 발 서기 → 부저 3회 |
| 4-2 안전모 | face authorized + helmet fail / vest pass | WARNING, '안전모 미착용' 카드 | 주황 눈 → 두 발 서기 → 부저 3회 |
| 4-3 조끼 | face authorized + helmet pass / vest fail | WARNING, '안전조끼 미착용' 카드 | 주황 눈 → 두 발 서기 → 부저 3회 |

- A가 얼굴과 PPE를 시차를 두고 보내면 그 사이에 노란 눈(PENDING)이 보일 수 있다. 보이면 7번 관찰로 기록한다.
- A 메시지에서 확인할 것:
  - 토픽: `mechdog/v1/vision/face`, `mechdog/v1/vision/ppe`
  - **face와 ppe의 session_id가 같은지**. 다르면 D가 다른 방문자로 처리한다.
  - `items.helmet`, `items.vest` 값

### 단계 5. 눈 색 / 두 발 서기 / 부저 3회 / 관리자 해제 확인
시나리오마다 다음을 기록한다.
1. 로그: `[state] ... -> ALERT/WARNING`, `alert/event` 발행, UDP 명령의 순서와 대상 IP
   - 순서: (노랑) → 빨강/주황 → `CMD|2|1|6|$` → `CMD|7|1|$`
2. 실물: 눈 색, 두 발 서기, 부저 3회와 그 순서
3. 화면: 배지(`/ 미해제 경고 N건`), 사유 카드
4. 관리자 해제 후:
   - 로그: `resolved=true`, 그리고 파랑 → `CMD|7|0|$` → `CMD|2|1|99|$`
   - 실물: 파란 눈, 기본 자세
   - 화면: '판정 대기(해제됨)'

- 결과표에는 실물과 화면을 직접 본 항목만 Pass로 적는다. 전송 성공 로그만으로는 Pass가 아니다.
- B/C가 실제 alert.event를 발행하면 10·11번(표시만 되고 로봇은 움직이지 않음)도 같이 관찰한다.

## 5. UDP 미수신 현상 — 원인 미확정 / 재발 가능

### 기록 (2026-10-03)
- 조끼 위반 시 대시보드 로그로는 UDP 4건이 오류 없이 전송됐지만, 로봇은 반응하지 않았다(파란 눈 유지).
- REPL 읽기 전용 확인 결과:
  - 직전 해제 명령 이후 로봇 WiFi 파서에 도달한 CMD 프레임이 없었다.
  - 재부팅은 없었다.
- 직후 ping은 4회 중 1회 timeout, 첫 응답 2474 ms였다.
- 이어서 보낸 식별 요청 `CMD|0|$` 1회는 파서에 도달했다.
- 10/04 시험(로봇 재부팅·IP 변경 이후)은 정상 동작했다.
- **원인은 확정되지 않았다.** 무선 구간에서 유실됐는지, 수신 후 파싱 전 단계(펌웨어 내장 WiFi 모듈)에서 버려졌는지 모른다.
  - 가설(미검증): 로봇이나 핫스팟의 WiFi 절전/재연결 때문에, 한동안 쉬다가 들어온 첫 패킷이 유실된다.
- **10/04 성공은 원인 해결을 뜻하지 않는다. 다시 발생할 수 있다.**
- 이 펌웨어는 UDP 응답을 보내지 않는다. 대시보드의 "전송 성공" 로그는 로봇이 받았다는 증거가 아니다.

### 현장에서 로봇이 반응하지 않을 때 확인 순서
명령을 자동으로 다시 보내거나 같은 명령을 반복 전송하지 않는다. 각 단계 결과를 시각과 함께 기록한다.

1. **대시보드 로그**를 본다.
   - 해당 시각에 `[state]` 전환과 `[D ROBOT][udp] SENT`가 있는지
   - 대상이 **현재 로봇 IP:9027**인지
   - `전송 실패` 메시지가 있는지

   결과에 따라:
   - SENT가 없으면: MQTT 수신 문제(토픽·session_id·브로커 주소)이거나 드라이버가 mock이다. 로봇 문제가 아니다.
   - IP가 다르면: 로봇이 재부팅되며 IP가 바뀐 것이다. 단계 2부터 다시 한다.
2. **화면**을 본다.
   - 드라이버가 `UDP(실물)`인지
   - 전송 오류 표시가 있는지
   - 활성 경고 상태: 같은 경고가 이미 활성이면 중복 방지 때문에 다시 보내지 않는 것이 정상이다.
3. **네트워크**를 본다. `ping <로봇 IP>`로 유실과 첫 응답 지연을 기록하고, `arp -a`로 로봇 MAC이 맞는지 확인한다.
4. **로봇 REPL**을 읽기 전용으로 본다. 에코를 대조하며 짧게 입력하고, Ctrl-C와 리셋은 쓰지 않는다.
   확인할 값: `wifi.wlan.isconnected()`, `wifi.wlan.ifconfig()[0]`, `_COMMAND`, `_REC_PARSE_VALUE`, `_buzzer_warn_state`, `time.ticks_ms()`
   - `_REC_PARSE_VALUE`가 직전 경고 명령이 아니라 그 전 명령에 머물러 있으면, 해당 패킷이 파서에 도달하지 않은 것이다.
   - `ticks_ms`가 작으면 재부팅된 것이다(IP가 바뀌었을 수 있음).
5. **경로 확인이 필요하면** 담당자 승인을 받고 `CMD|0|$`(식별 요청, 눈·자세·부저와 무관)를 1회만 보낸 뒤 4번을 다시 본다.
   도달하더라도 "원인 해결"로 판단하지 않는다.
6. 그래도 안 되면 그 시나리오를 **Fail/보류로 기록**하고 다음으로 넘어간다.
   결과표에는 현상 / 확인한 것 / 미확인 / 후속 작업을 적는다.

### 남은 후속 작업 (미착수)
- 쉬다가 들어온 첫 패킷이 유실되는 현상의 재현 조건 확인(얼마나 쉬면 발생하는지)
- 대책 후보(미결정). 모두 팀/멘토와 결정한 뒤 진행한다.
  - 경고 직전에 무해한 패킷을 먼저 보내기
  - 핫스팟/로봇 절전 설정 확인
  - 수신 확인(ACK)을 펌웨어에 추가
